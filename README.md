## 1. システム概要

### 開発目的

上司とメンバーが1on1を行いながら、目標や次の行動、進捗を簡単に整理することを目的としています。

本人が編集し、上司は閲覧リンクから同じ内容を確認します。
入力項目と画面遷移を絞り、会話中でも操作しやすい構成を目指しました。

### 主要機能

| 機能 | 内容 |
|---|---|
| 基本情報 | メンバー名・実施日・入職年月。業界歴を自動計算 |
| 目標管理 | 取り組み中の目標を最大3件まで登録 |
| タスク管理 | 目標ごとに最大3件。期限・優先度・完了状態を管理 |
| 進捗表示 | 完了タスクの割合を表示 |
| 達成・継続 | 全件完了後、確認して達成済みにするか継続するかを選択 |
| 履歴 | 基本情報・目標・タスク・進捗を最新3回分保持 |
| リンク共有 | 編集用と閲覧用を分離。ログイン不要 |

画面は、暗い夜の街をイメージした配色と、小さな静止ドット絵を取り入れています。（自分の好きな世界観を取り入れたかったため夜をテーマにサイバーな雰囲気を取り入れています。）
業務利用を前提に、日本語本文や入力欄の読みやすさを優先しています。

## 2. アイデア出し・要件定義

AIと会話しながら自然言語でアイデアを練り上げました。
特に、1on1の会話を想定して、必要な機能と追加しない機能を決めました。

### 対話を通じて具体化した要件

- 取り組みを増やしすぎないよう、目標・タスクをそれぞれ3件までにする
- 履歴は「過去3ヶ月」ではなく「最新3回分」にする
- 全タスクが完了しても、自動で目標を消さない
- 達成済みの目標は、次の1on1で振り返ってから削除できるようにする
- 業界歴は年数の手入力ではなく、入職年月から計算する
- アカウント管理を追加せず、編集／閲覧リンクで共有する

### 優先順位

1. 正しい保存とデータ保護
2. 編集・閲覧の権限制御
3. 少ない操作と分かりやすい表示
4. 軽量な装飾による親しみやすさ

サブタスク、通知、リアルタイム共同編集、アプリ内AI機能などは対象外としています。

## 3. 設計

画面、業務ルール、保存処理を分離しました。
初期のブラウザ内保存から、ローカルサーバー、Workers＋D1へ段階的に拡張しています。

### データ設計

ルームごとに、以下の4カラムを持つ1行を保存します。

| カラム | 内容 |
|---|---|
| `id` | ルームID |
| `state` | 基本情報・目標・タスク・履歴・revisionを含むJSON |
| `edit_hash` | 編集トークンのSHA-256ハッシュ |
| `view_hash` | 閲覧トークンのSHA-256ハッシュ |

履歴は現在データの独立したコピーです。
現在の目標を編集・削除しても、保存済みの履歴へ連動させません。

保存時にはrevisionとDBの現在状態を確認し、古い画面からの上書きを拒否します。

## 6. 開発環境・環境操作

### 使用技術

| 項目 | 技術・構成 |
|---|---|
| フロントエンド | HTML、CSS、JavaScript／ES Modules |
| 本番バックエンド | Cloudflare Workers |
| 本番DB | Cloudflare D1 |
| 静的配信 | Workers Static Assets |
| 開発・テスト | Node.js 24系、Node標準テスト機能、Node内蔵SQLite |
| CLI | Wrangler。現在のlockでは4.158.0 |
| コード管理 | Git、GitHub |
| 自動デプロイ | Cloudflare Workers Builds |

### 環境の分離

- 本番設定：`wrangler.jsonc`
- ローカル設定：`wrangler.local.jsonc`
- D1接続：`DB` binding
- 静的ファイル：`ASSETS` binding
- DB・秘密情報・エクスポートなどはGitの除外対象

本番とローカルでは保存先が異なります。
データを自動で移行・削除する構成にはしていません。

## 7. コードの品質担保

正常な操作だけでなく、「できてはいけない操作が拒否されること」を重視しました。

### テストの観点

- 目標・タスクの上限と入力制限
- 進捗計算
- 完了タスクの編集ロックと、継続時の解除
- 履歴の最新3回保持と、現在データからの独立
- 閲覧リンクによる更新の禁止
- 保存競合と、保存失敗時のデータ保護
- Workerの起動入口と、公開ファイルの範囲

自動テストは計30件あり、開発時に成功を確認しています。

D1関連の自動テストは、Node SQLiteによる互換環境です。

### セキュリティ・エラー対応

- 共有トークンを暗号学的乱数で生成
- DBにはトークンのハッシュだけを保存
- API側で権限・入力・状態を検証
- SQLの値をバインドして実行
- 公開する静的ファイルを許可リストで限定
- 保存失敗時は入力を保持し、成功表示にしない
- 内部エラーや秘密情報を応答へそのまま出さない

リンクを持つ人がアクセスできる方式です。

### 今後の品質改善

- 実D1を使った自動テスト
- 別PC・別ブラウザでの検証拡充
- 本番での権限拒否・削除操作の追加検証
- 性能・負荷測定
- バックアップ復元と運用手順の確認
- 公開情報の継続的な監査

## 8. 基本的な使い方

1. 公開URLで基本情報を入力し、ルームを作成する
2. 編集リンクを本人が保管し、閲覧リンクを上司へ渡す
3. 目標とタスクを登録し、「変更を保存」を押す
4. タスクを完了し、全件完了後に達成または継続を選ぶ
5. 1on1の終了時に、保存後「今回の1on1を記録」を押す
6. 閲覧者は「最新情報に更新」で保存済みの内容を確認する

通常の完了タスクは編集・削除できません。
必要な場合は、目標の継続・再開を選びます。

達成済み目標は、達成日より後の1on1で最新内容を記録した後、確認して現在画面から削除できます。
保存済みの履歴は残りますが、履歴自体も最新3回の保持制限を受けます。

## 9. AI活用で得られた知見

### 効果があったこと

- 実装だけでなく、テストまで一貫して対応してもらえた
- サブエージェントがチームのように作業を分担できた

### 難しかったことと改善

対話だけで指示すると、変更したい項目が抜けたり、指示していない場所まで変更されたりすることがありました。

そこで、別のプロンプト生成用チャットで依頼をMarkdownに整理し、変更箇所を絞って実装担当へ渡すようにしました。

指示では、次を明確にすることを重視しました。

- 何のために変更するか
- どこを変更するか
- 何を変更しないか
- 維持する仕様・データは何か
- 何を確認すれば完了か
- 不明点を推測せず確認すること

AIに実装とテストを任せても、仕様の判断と結果の確認は人間側に残ります。
今後も、指示内容と実装・テスト結果を対応させながら活用していきます。
