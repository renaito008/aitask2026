## 1. 根拠と情報の区分

初期SPEC.md 1.0.0、現行docs/SPEC.md 1.2.0、画面・業務ルール・Worker・設定・テストコードを読み取り調査した。
公開状況と過去のテスト成功は開発時の確認記録に基づく。今回、アプリ操作やテスト再実行はしていない。
旧資料の「未公開」「公開先未決定」は当時の記録として扱う。未確認事項は実施済みとしない。

## 2. 開発目的

1on1の会話を止めずに、目標・タスク・進捗を簡単に整理する。
本人が操作し、上司は閲覧リンクから同じ内容と過去の記録を確認する。
入力と画面遷移を減らし、取り組みを増やしすぎず、前回からの変化を振り返れるようにする。
軽量さと読みやすさを優先し、夜の街・ドット絵の親しみやすさを加える。

## 3. 利用者と権限

| 対象 | 権限 |
|---|---|
| 編集リンクを持つ人 | 基本情報・目標・タスクの操作、履歴記録、条件付き削除、リンク再発行 |
| 閲覧リンクを持つ人 | 保存済みの現在データと履歴の閲覧のみ |

1ルームは1人分。複数メンバーの一覧管理は提供しない。
ログインや管理者アカウントは追加しない。本人確認ではなく、リンクの所持に基づくアクセス権とする。
本人は編集リンクを保管し、相手には閲覧リンクだけを共有する。
共同編集の自動統合やリアルタイム同期は行わず、閲覧者が「最新情報に更新」で取得する。

## 4. 優先順位

1. 業務ルールに従って正しく保存し、競合・失敗でデータを失わない。
2. サーバー側で編集・閲覧権限を分ける。
3. 少ない入力で状態と進捗を把握・更新できる。
4. 動作負荷を抑えた装飾で親しみやすさを加える。

## 5. 機能要件

### FR-01 基本情報

- メンバー名、1on1実施日、IT業界への入職年月を入力する。
- 名前は空白のみ不可・最大50文字。実施日は有効な日付、今日以前、入職年月以降とする。
- 入職年月は当月以前とし、業界歴を月単位で自動計算する。
- 現在画面は現在時点、履歴は実施日時点の業界歴を表示する。
- 所属・住所・生年月日・メールなどの入力項目を追加しない。

### FR-02 目標

- 取り組み中は最大3件。達成済みは枠から外す。
- 目標名・期限を扱う。名前は空白のみ不可・最大100文字。
- 取り組み中と達成済みを分けて表示する。
- 取り組み中の目標は確認後に削除できる。ただし通常状態で完了タスクを含む場合は拒否する。
- 目標削除では現在のタスクも削除するが、保存済み履歴は変更しない。

### FR-03 タスク

- 目標ごとに最大3件。完了タスクも件数に含める。
- タスク名・期限・優先度（低・中・高）・完了状態を扱う。
- 名前は空白のみ不可・最大100文字。期限は日付単位で、過去日も指定可能。
- 未完了は編集・確認付き削除が可能。通常の完了タスクは編集・削除・完了解除を禁止する。
- 継続・再開を明示した目標では完了タスクも再編集できる。
- 期限より今日が後、かつ未完了なら期限切れと表示する。当日や完了済みは対象外。
- サブタスク・階層を追加しない。

### FR-04 進捗・達成・継続

- 進捗は完了数÷総数を整数に丸める。タスク0件は0%。重み付けはしない。
- 達成判定は「1件以上あり全件完了」。表示率の丸め値で判定しない。
- 最後のタスク完了時に確認を出し、自動削除・自動移動しない。
- 「達成済みにする」で達成済み欄へ移し、「まだ取り組む」で取り組み中に残して再編集可能にする。
- Escなどで閉じただけなら取り組み中に残し、完了ロックは解除しない。
- 達成済みから再開する場合は取り組み中の枠に空きが必要。完了状態は自動で解除しない。
- 通常の変更は「変更を保存」で確定する。

### FR-05 履歴

- 基本情報、取り組み中・達成済みの全目標、全タスク、期限、優先度、完了状態、進捗をコピーして記録する。
- 秘密トークンは履歴へ含めない。現在の編集・削除を過去のコピーに連動させない。
- 実施日順で最新3回を保持する。3ヶ月ではない。
- 同日は確認後に上書きし、別の回を増やさない。
- 4回目の記録成功時に実施日が最も古い回を保持対象から外す。
- 3回保持中に、それより古い実施日を新規記録する操作は拒否する。
- 記録と間引きは一括確定。失敗時は以前の履歴を維持する。
- 履歴の直接編集は不可。同日の再記録だけを更新手段とする。

### FR-06 達成済み目標の振り返り・削除

- 次の1on1まで残し、自動削除しない。
- 実装上は達成日より後の実施日で、同じ目標の最新revisionを達成済みとして記録していることが削除条件。
- 同日の記録だけでは条件を満たさない。
- 記録成功後、確認して現在画面から削除できる。保存済み履歴は残す。
- 再開・変更後の目標を、変更前の記録だけで削除できない。

### FR-07 保存・競合

- 未保存状態を表示し、未保存のまま履歴記録しようとしたら保存を促す。
- 保存失敗を成功扱いにせず、入力を保持する。
- revisionとDBの現在状態を比較し、古い画面からの保存を拒否する。
- 競合を自動統合せず、入力を控えて最新情報を取得するよう案内する。

### FR-08 共有リンク

- 編集・閲覧トークンを別々に発行し、閲覧権限の変更をAPI側で拒否する。
- 編集者は閲覧・編集・両方のリンクを再発行でき、対象の旧リンクを即時失効させる。
- 閲覧者にはリンク再発行や編集リンク取得を提供しない。
- 失った編集リンクをアカウントやメールで復旧する機能はない。

## 6. 非機能要件

| 項目 | 方針 |
|---|---|
| 操作・表示 | 選択・ボタン中心、入力と遷移を抑える。未保存・拒否理由を表示 |
| デザイン | 暗い背景、小さな静止ドット絵、日本語本文の可読性を優先 |
| 軽量性 | 大きなUIライブラリ、動画背景、大量の粒子、常時動く雨を追加しない |
| 保守性 | 画面、業務ルール、保存処理を分離 |
| セキュリティ | 安全な乱数、ハッシュ保存、API権限検証、入力検証、配信範囲の限定 |
| 整合性 | 保存競合を拒否し、履歴・トークンを原子的に更新 |
| 公開 | Workers＋D1、GitHub mainからの自動デプロイ |
| コスト | 無料枠を前提とするが、実際の料金・利用量を保証しない |

性能目標値、SLA、想定同時利用人数、対応ブラウザの保証範囲、バックアップのRPO/RTOは未定義・要確認。

## 7. 対象外

管理者ログイン、社員アカウント認証、上司の編集、多人数一覧、共同編集、自動同期、通知、メール、サブタスク、ポイント・ランキング、アプリ内AI。
Codexは開発支援に利用し、アプリ利用時にOpenAI APIを呼ぶ構成ではない。

| 段階 | 内容 |

| 公開・GitHub連携 | 手動公開後、mainへのpushによる自動デプロイ成功を確認 |

対話中に履歴を「3ヶ月」から「3回」へ具体化し、細分化を制限し、達成時の確認などを決定した。
文章化済みの初期要件には既に反映されており、すべてが実装後の変更だったとは扱わない。
