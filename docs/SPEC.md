# 目的と仕様の扱い

## GitHub復旧待ちの最新指示（2026-11-08）

既存WorkerへのCLI公開はユーザー承認済み。ユーザー環境で実Wrangler local起動と編集/閲覧の確認が完了している。親環境のCloudflare whoamiは未認証のため、認証確認後に親担当が公開を判断・実行する。GitHub復旧後は既存WorkerのWorkers Buildsへ接続し、GitHub Actionsは追加しない。

この準備ではコード・lock・依存許可を保持し、Git除外、候補監査、ローカルrelease準備、手動deploy補助と手順だけを追加する。実装担当はpush/remote作成/デプロイ/remoteDBを行わない。破壊的変更・既存データの移行/削除は別途事前確認を必要とする。以前の「Wrangler未導入」「今回公開しない」は過去フェーズの記録であり、この最新状況と区別する。

## Workers + D1追記（2026-11-08・最新指示）

Cloudflare Workersと既存D1へ対応する。Worker名task-management-api、D1名task-management-db、binding DB、database_id 81918d83-4f0e-4827-baa6-042b890efeeb。rooms(id TEXT PRIMARY KEY,state TEXT NOT NULL,edit_hash TEXT NOT NULL UNIQUE,view_hash TEXT NOT NULL UNIQUE)とstate JSONは維持する。編集/閲覧リンク方式を保ち、ログイン・管理者アカウントは追加しない。画面のデザイン・操作・項目はそのまま。Workers配信時だけ保存先の環境説明をD1向けに置換する。

サーバーAPIはWeb標準APIとD1 bindingで実装。Node http/fs/sqliteはWorker実行コードへ持ち込まない。単一UPDATEのfull-state/hashes比較CASで、履歴3件への間引きとトークン再発行を含めて原子的に確定する。競合は409、失効した編集リンクは401、閲覧による変更は403。静的公開資産はpublicへホワイトリストコピーし、DB・ドキュメント・テスト・サーバーソースは公開しない。

元のSQLiteを自動移行・変更しない。明示的なread-only exportだけを用意し、state文字列とハッシュをそのまま保存。同一ID/全値一致はno-op、差異はNOT NULL違反で単一SQL全体を中止する。大きなJSONの自動移行は未対応。remote操作は実施していない。

実装担当はコード・ローカル検証まで。親担当/ユーザーが本物Wranglerでのローカル確認と接続権限を確認し、その結果をもってデプロイを判断する。今回の環境にはWrangler/Miniflareがなく、NodeSQLite D1 shimでの検証は実Cloudflare D1の成功を意味しない。ユーザーの最新指示は「まずlocal環境で動作確認、問題なければdeploy」であり、それ以前の公開禁止説明は過去フェーズの記録として残す。

## フェーズ2追記（2026-11-01）

今回の継続開発では、下記「初回実装の範囲」はフェーズ1の履歴として残し、次段階のローカルサーバー保存・編集/閲覧リンク・サーバー側権限検証・DBでの履歴トランザクションまで進める。Node同梱SQLiteはローカル検証用のRepository実装であり、本番DB・無料公開先を確定したものではない。実データ・課金・契約・公開は行わない。

既存localStorageは変更せず `/demo` に残す。新規ルーム作成は基本情報から行い、自動移行・自動破棄を行わない。リンクは暗号学的ランダムな256bitトークンを用い、DBにはハッシュだけを保存する。閲覧権限はAPIで強制し、全変更はrevisionを照合する。履歴や閲覧レスポンスに編集トークンを含めない。

初期実装案としてHTTPは127.0.0.1のみにbindし、URL fragmentで渡したトークンは読込直後にURLから除去してタブのsessionStorageへ保持する。通信はAuthorizationヘッダーを使い、アクセスログへ記録しない。リンク再発行は編集用・閲覧用・両方を選べ、対象の旧リンクを直ちに無効化する。再発行と状態保存は同一トランザクションで行う。アカウント・リアルタイム同期は追加しない。

この段階の独立ブラウザcontext検証は別PCでの接続検証の代わりではない。別PC接続と公開環境でのHTTPS等は次段階とする。

上司とメンバーが別々のPCから目標・タスク・進捗を確認するWebアプリを作る。操作はメンバー一人のみ、上司は閲覧のみ。1on1の会話を止めない簡単な入力・選択・ボタン操作を重視する。

これはアプリの仕様であり、過去に作成したHTML発表スライドをアプリへ変換する指示ではない。発表資料のindex.html、style.css、script.jsは編集・削除しない。アプリは別の専用プロジェクトで作る。

本書の「確定」はユーザーが決めた仕様。「実装案」は未指定の細部に対する提案であり、ユーザーの確定事項として扱わない。仕様を変更する場合はユーザーの指示を反映して版番号と変更履歴を更新する。チャットの記憶だけで仕様を補わない。

# 確定仕様

## 1. 利用者・共有

- メンバーは基本情報、目標、タスクを操作できる。
- 上司は現在の内容と履歴を閲覧できる。登録・編集・削除・達成・再開・記録・リンク発行はできない。
- 本番では編集用リンクと閲覧用リンクを分ける。編集用は本人だけが保持し、上司には閲覧用を共有する。
- 本番では推測しにくいリンクを用い、無効化・再発行に対応する。無効化後の旧リンクは利用できない。
- 本番の閲覧権限はサーバーでも強制する。編集ボタンを隠すだけでは完成としない。
- 最初の共有版では上司の「最新情報に更新」ボタンで情報を読み込む。リアルタイム同期・共同編集は今回不要。
- リンクを知る人にアクセスを許可する方式。初版ではログインやアカウント管理を追加しない。

## 2. 基本情報

- メンバー名。
- 1on1実施日。最新実施日を基本情報へ表示し、各回の内容を履歴に保存する。
- IT業界への入職年月。年・月を選び、業界歴を自動計算する。
- 業界歴は月単位の経過年月。計算結果が負にならないよう検証する。
- 現在の画面では当月時点の業界歴、履歴ではその1on1実施日時点の業界歴を表示する。
- 所属、メール、住所、生年月日などの項目を追加しない。

## 3. 目標

- 取り組み中の目標は一人につき最大3件。達成済み目標はこの枠に含めない。
- 目標名と期限を扱う。
- 登録済み件数と上限を表示する。上限時は追加できず、理由を表示する。
- タスクが0件の場合、進捗は0%で、達成済みにできない。
- 進捗は「完了したタスク数 / 登録済みタスク数」。タスクの難しさによる重み付けは行わない。
- 表示する率は整数に丸めるが、達成判定は率の丸め値でなく「タスクが1件以上あり、全件が完了」で行う。
- 未完了のタスク追加・削除時には進捗を再計算する。

## 4. タスク

- 一つの目標につき最大3件。完了したタスクも件数に含める。
- 入力はタスク名、期限、優先度。完了チェックを用意する。
- 優先度は低・中・高の選択式。
- サブタスク、ステップ、チェックリスト、階層の追加は禁止。
- 完了したタスクは目標の達成確認まで消さず、その後も達成済み目標と一緒に残す。
- 通常状態の完了タスクは編集不可。削除・完了解除を含めてロックし、回避操作を設けない。
- 「取り組みを続ける」操作による継続状態では再編集でき、必要に応じて未完了へ戻せる。
- 未完了タスクは編集できる。削除は確認後に行い、進捗を再計算する。
- 期限は時刻を含めない日付。過去の日付も登録可能。期限を過ぎた未完了タスクに印を付ける。
- 当日期限は期限切れとしない。完了タスクに期限切れの印を付けない。

## 5. 達成・継続

- 最後のタスクを完了すると確認ダイアログを表示する。
- 100%になった瞬間に目標を自動削除・移動しない。
- 「まだ取り組む／取り組みを続ける」を選ぶと、取り組み中の枠に残り、タスクを再編集できる継続状態になる。
- ダイアログを閉じただけの場合は、取り組み中のまま残す。閉じるだけで編集ロックを解除しない。
- 「達成済みにする」を選ぶと、目標とタスクを達成済み欄へ移動する。
- 達成済み欄から「取り組みを続ける」を選ぶと、取り組み中へ戻り、タスクを再編集できる。
- 再開先に取り組み中の目標が3件ある場合は再開できず、理由を表示する。
- 再開時には既存の完了状態を維持する。自動で全タスクを未完了にしない。
- 取り組み中に残した100%の目標は、後から手動で達成済みにできる。

## 6. 達成済み目標の振り返り・削除

- 達成済み目標は次の1on1まで残す。
- 次の1on1で振り返り、「今回の1on1を記録」で目標・タスクを履歴に保存する。
- 保存が成功した後、確認して現在の達成済み欄から削除できる。
- 自動削除しない。記録に失敗した場合は削除を許可しない。
- 現在の画面から削除しても、既に保存した履歴内の目標・タスクは残す。
- 再開後に変更された目標を、変更前の記録だけを根拠に削除してはならない。

## 7. 1on1履歴

- 基本情報、全目標、全タスク、期限、優先度、完了状態、各目標の進捗を、その時点の内容で丸ごと保存する。
- 取り組み中と達成済みの目標を両方保存する。リンクの秘密情報は履歴に含めない。
- 履歴はコピーとして保存する。現在の編集が過去の履歴に反映されないこと。
- 最新から遡って3回分だけ保持する。3ヶ月分ではない。
- 最新は実施日順。同じ実施日は同じ回として扱う。
- 同じ実施日で再記録する場合は確認して上書きする。別の履歴を増やさない。
- 異なる実施日で新しく記録し、4回分になったら実施日が最も古い1回をDBから削除する。
- 新規保存／上書きと古い記録の削除は一括処理。失敗時には以前の記録を維持する。
- 履歴そのものの直接編集は不可。同日の再記録だけが内容更新の手段。
- メンバーと上司の両方が履歴を閲覧できる。

## 8. 保存

- 「保存」ボタンで変更を確定する。未保存の変更があることを表示する。
- 保存失敗時は成功扱いにしない。入力内容を維持し、再試行できる。
- 「今回の1on1を記録」は保存済みの現在データを対象にする。未保存データがある場合は先に保存するよう案内し、黙って別の内容を記録しない。
- 破壊的な操作には確認を表示する。

# 実装案（確定事項ではない）

以下は初回試作のデフォルト案。既存コードやユーザー指示と衝突する場合は変更理由を説明する。

- 日付はAsia/Tokyoを基準にする。日付文字列はYYYY-MM-DD、入職年月はYYYY-MM。UTC変換で日付をずらさない。
- 未来の実施日での履歴記録、未来の入職年月を拒否する。
- 目標名・タスク名は空白のみを不可、最大100文字。メンバー名は空白のみを不可、最大50文字。
- タスク・目標の期限は必須。入力前に必須表示を付ける。
- 3件の履歴がある場合、保持範囲より古い実施日を新規記録する操作は拒否し、理由を表示する。
- 初期優先度は「中」。空の目標・タスクを勝手に追加しない。
- 新しい全件完了への遷移時のみ達成確認を自動表示する。画面再描画・保存・読み込みのたびに再表示しない。
- 達成後の初回振り返りは、達成時より後の日に実施した1on1の記録を条件とする。同日振り返りの扱いは本番実装前に確認する。
- 一つの管理領域は一人のメンバーに対応する。複数メンバーを一覧管理する画面は追加しない。

# 推奨データの境界

画面は保存先を直接操作しない。例として次のモデルを使えるが、フィールド名の選択は実装担当に任せる。

- Profile: memberName, joinedMonth, latestMeetingDate
- Goal: id, title, dueDate, status(active/achieved), continuationEditEnabled, achievedAt, revision, tasks
- Task: id, title, dueDate, priority(low/medium/high), completed
- MeetingSnapshot: id, meetingDate, recordedAt, profile, goals, goalProgress
- AppState: schemaVersion, profile, goals, snapshots, revision

履歴では入職年月だけでなく実施日時点の年月数も保持できるようにする。目標の改訂番号などで、削除前の振り返り記録が最新内容を含むか確認する。currentデータの削除がsnapshotへ連鎖しない設計にする。編集／閲覧リンクのトークンをsnapshotへコピーしない。

# 完成条件・検証項目

1. 取り組み中の目標の4件目を追加できない。
2. 達成済みの目標は取り組み中の3枠に数えない。
3. 各目標のタスク4件目を追加できない。完了タスクも枠に含まれる。
4. サブタスクの画面がない。
5. タスク0件は0%、1/3は33%、2/3は67%、3/3は100%で表示される。
6. 通常の完了タスクの名前・期限・優先度・削除・完了解除はロックされる。
7. 全タスク完了で確認が出る。閉じても目標が消えない。
8. 継続を選ぶと100%の目標が枠に残り、再編集できる。
9. 達成を承認すると、目標とタスクが達成済み欄へ移る。
10. 達成済みからの再開は空き枠があるときだけ可能。
11. 再開で既存の完了状態が勝手にリセットされない。
12. 入職年月から正しく年月数を計算し、年またぎ・0ヶ月・未来年月を検証する。
13. 期限が今日の未完了タスクは期限切れと表示されない。
14. 保存後の再読み込みでローカルデータを復元できる。
15. 保存失敗時に入力と以前の保存データを失わない。
16. 未保存の変更があるときに以前の保存内容を黙って履歴記録しない。
17. 同じ実施日の再記録は確認して上書きされる。
18. 異なる実施日を4回記録すると最新3回が残り、古い1回は保存領域から消える。
19. 履歴は現在の編集・再開・削除によって変化しない。
20. 履歴保存失敗時に古い履歴や達成済み目標が消えない。
21. 振り返り未記録の達成済み目標を削除できない。
22. 記録済みの達成済み目標を確認して削除でき、履歴には内容が残る。
23. 閲覧モードには変更操作がなく、状態変更処理からも変更を拒否する。試作のモードは本番の権限保証でないと明記する。
24. キーボードで主要操作が可能。確認ダイアログの初期フォーカス・キャンセル・閉じた後のフォーカスを確認する。
25. 1280×720と1920×1080で入力・一覧が重ならない。画面を超える内容は適切にスクロールできる。
26. 過去の発表資料を変更していない。
